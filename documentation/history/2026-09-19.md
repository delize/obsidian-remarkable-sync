# 2026-09-19: Sanitise invalid filename characters before they become vault paths

## Accomplished

Notebook names came from the device and reached `vault.createBinary` with no checking at all.
A `/` silently created nested folders instead of one file; `: * ? " < > |` broke on Windows and
Android, so a vault written on a Mac stopped working once synced; `[ ] # ^ |` broke the wikilink
the highlights note emits; and a hand-edited `data.json` with `"targetFolder": "../../etc"`
survived verbatim.

Six commits:

1. `src/utils/sanitise-path.ts` — `sanitiseName`, `sanitiseRelativePath`, `validateVaultFolderPath`.
2. Sanitisation wired into `buildPagePath` and `buildDocumentPath`, plus wikilink agreement.
3. Folder-vs-file guards in `writeBinaryIfChanged` and `ensureParentFolder`.
4. `src/app/services/output/legacy-paths.ts` — detect and report, called once per notebook from
   both orchestrators.
5. `targetFolder` validated in `settings-tab.ts` and `load-settings.ts`.
6. Documentation.

This closes a defect deferred twice: `2026-08-01.md` lines 293-299 ("Worth a separate fix") and
`2026-08-20.md` lines 106-112 ("changing it alters existing vaults' layouts, so it needs its own
decision"). The incident recorded at `plans/match-remarkable-export.md` lines 10-17, where a device
document named `sample (annotated)` caused the plugin to overwrite a file believed to be
reMarkable's own reference export, is the collision this work was prompted by — but see
"Known, not fixed": that particular collision is NOT fixed.

## Decisions

- **The union of every platform's rules, applied on every host**, not the host's own set. The
  machine that writes a bad name is not the machine that discovers it.
- **Sanitise in the path builders, not at the write call.** `writeBinaryIfChanged` is the single
  write funnel but it is too late: once the components are joined, a `/` that came from inside a
  notebook name cannot be told apart from a separator the builder added.
- **`folderPath` is split and sanitised per segment.** It arrives pre-joined from
  `remarkable-cloud.service.ts`, so treating it as one name would flatten a real hierarchy into a
  single hyphenated folder.
- **Idempotence is a requirement, not a nicety.** The migration reporter compares an old path
  against a new one; if a clean name did not survive unchanged, every notebook in the vault would
  look like it had moved, forever.
- **Truncation appends a discriminator.** The ` (annotated)` suffix is added by the caller BEFORE
  sanitising, so a long `X` and the same name plus the suffix would otherwise truncate to the same
  string and the annotated PDF would overwrite the source — strictly worse than the over-long name.
- **`normalizePath` deliberately not used.** It carries no doc comment and guarantees nothing about
  illegal characters, and its Unicode NFC normalisation would change the bytes of paths written by
  earlier versions on macOS, defeating the skip-if-unchanged write guard.
- **Windows reserved device names handled**, despite the source forum thread not raising them.
  Omitting them would make the character rule portable and the name rule not.
- **The wikilink fix is agreement, not a second escape set.** The link target and the written file
  name were built by two separate expressions, so sanitising the writer alone would have left the
  note pointing at a name that no longer exists. Both now derive from `documentFileName`. An escape
  tuned for wikilink syntax would have produced a link matching no file at all.
- **Detect and report, never mutate.** The plugin does not move, rename or delete a vault file.
- **Settings validated differently at each boundary**: refused in the pane (rewriting what someone
  just typed is worse than explaining), sanitised with a warning on load (non-interactive, must not
  break startup).

## Correctness review, and what it changed

An adversarial review plus a 1.8M-name fuzz sweep found `sanitiseName` was **not idempotent**,
contradicting the requirement recorded above. Two independent ORDERING bugs, neither visible
without running the function twice:

1. **`.trim()` ran AFTER the leading-dot replacement.** `^\.+` does not match `" .hidden"`, so any
   whitespace that `trim` removes but that is not a control character (space, NBSP, BOM) hid the dot
   from the anchor. The dot then survived into the vault, and Obsidian excludes dot-prefixed files
   from the index entirely. With the default empty `targetFolder`, output could land in `.obsidian/`,
   `.git/` or `.trash/`. Fix: trim first.
2. **Stripping a trailing dot EXPOSED whitespace the trim had already passed.**
   `TRAILING_DOTS_AND_SPACES` was `/[. ]+$/`, matching only a literal dot and an ASCII space, so a
   trailing BOM or NBSP behind a dot survived pass one and was removed on pass two. A leading trim
   alone does NOT fix this. Fix: the trailing class is now `/[\s.]+$/`, covering every character
   `trim` would take.

Downstream, the first bug made the plugin write a dead wikilink into its own highlights note: the
file landed at `.Notes (annotated).pdf` while the link read `[[-Notes (annotated).pdf]]`.

Also fixed in the same pass:

- **Reserved device names missed `NAME.ext`.** The code tested the whole component, so `nul.tar` and
  `AUX.notes` passed through and failed on Windows with a bare `EINVAL`. Windows reads the text
  before the FIRST dot. The hyphen now goes on the STEM (`nul-.tar`), because suffixing the whole
  component would leave the stem reserved and grow another hyphen on every pass. `com0`/`lpt0` and
  the superscript forms (`COM\u00b9`) were also missing.
- **A false claim in the `MAX_NAME_BYTES` comment.** It said 150 bytes "keeps a nested path clear of
  Windows' 260-character path limit". It does not: `buildPagePath` spends the name twice, so two
  names at the cap exceed 260 on their own. The comment now says what the cap actually buys.
- **An orphaned doc comment.** `toWikilinkTarget` had been inserted between `buildHighlightsNote`'s
  doc comment and its declaration, leaving the byte-identical-output constraint attached to the
  wrong function.
- **Log volume.** The reporter logged one `warn` per pair per sync, so 50 affected notebooks meant
  300 identical lines every cycle, forever. Now one summary line per notebook at `warn`, the pairs
  at `debug`.
- **`buildPageFolderPath` extracted.** The reporter derived the image folder by building a page path
  and dropping the last segment, which silently assumed the file name never contains a `/`.

Every fix was mutation-checked: reverting the trim order, the trailing character class, or the
reserved-name stem each makes specific named tests fail.

## Verification

`bun run tsc`, `bun run lint --max-warnings 0`, `bun run rules:check` and `bun test` (587) all
clean, plus `bun run build`.

Idempotence is now fuzz-verified rather than asserted: 1.8M generated names across five seeds and
three length bands, over an alphabet dense in the branch-driving characters (every unsafe character,
dots, spaces, NBSP, zero-width space, ideographic space, BOM, tab, newline, control bytes, CJK and
an astral emoji). Clean on idempotence, the byte cap, unsafe-character survival, empty results, and
`sanitiseRelativePath` idempotence.

Every new test was mutation-checked rather than assumed:

| mutation                                                | failures |
| ------------------------------------------------------- | -------- |
| sanitisation removed from the builders and the wikilink | 8        |
| both path-conflict guards removed                       | 2        |
| both `targetFolder` validations removed                 | 4        |

**Manual runtime verification still required.** A green build cannot show UI behaviour. Check in a
live vault: (i) a device notebook named with a `/` produces one file, not two folders; (ii) the
legacy-path Notice reads sensibly and names both paths; (iii) the settings pane shows an inline
error for `rM:notes` rather than silently rewriting it.

## Environment note

`bun run setup` arms the git hooks, and both of them use `mapfile`, a bash 4+ builtin. macOS ships
bash 3.2, so on a Mac the hooks fail with `mapfile: command not found` and no commit can complete.
Worked around here by installing bash 5 via Homebrew, which the `#!/usr/bin/env bash` shebang then
picks up. Worth fixing upstream — a `while IFS= read -r -d ''` loop would be portable.

## Known, not fixed

1. **`X (annotated)` versus the annotated copy of `X`.** Parentheses are not sanitised, and must
   not be, because the output suffixes depend on them. A device document literally named
   `sample (annotated)` still resolves to the same path as the annotated copy of `sample`. This is
   the mechanism behind the `match-remarkable-export.md` incident and it is unchanged. A fix needs a
   reserved-suffix check in `document-output.service.ts`, which is its own decision because it also
   changes where files land.
2. **Two notebooks sharing a `visibleName` in one folder.** The device keys on `id`, the vault on
   path, so the second overwrites the first on every sync. Sanitisation slightly WIDENS this:
   `Q3/Q4` and `Q3-Q4` were distinct before and now collide. A fix needs an id-derived suffix.
3. **Case-insensitive collisions.** `getAbstractFileByPath` is documented case-sensitive, so
   `Meeting notes` and `meeting notes` are two paths to the plugin and one file on APFS or NTFS.
   The legacy-path reporter cannot see these either, for the same reason.
4. **A `/` inside a reMarkable folder name is lost before the writer sees it.**
   `remarkable-cloud.service.ts` lines 139-153 joins folder names with `/` into a single
   `folderPath`, so `sanitiseRelativePath` cannot tell a genuine hierarchy separator from a slash
   inside one folder's name — a device folder called `Q3/Q4` still becomes two vault folders. The
   one-line fix is at line 147, but `folderPath` is also the panel's display value
   (`remarkable-panel-view.ts` lines 265 and 338), so it changes what the sidebar shows. Its own
   decision.
5. **Truncation collisions** are reduced to a hash collision by the discriminator, not eliminated.
6. **The reporter cannot see a `targetFolder` that moved.** `load-settings.ts` sanitises that value
   on the way in, so what reaches `buildLegacyPathPairs` is already clean and compares equal to
   itself. Only `folderPath` and `notebookName` arrive raw. Reporting it would mean keeping the
   pre-sanitisation value in the settings schema.
7. **`targetFolder` is sanitised in memory only.** `data.json` keeps the invalid value, so the
   settings pane shows the rewritten one and the file disagrees until something saves.
8. **`[ ] # ^` are refused in folder segments too**, which rejects folder names Obsidian itself
   accepts, `#inbox` being the obvious one. That follows from the decision to apply one union set
   everywhere rather than a per-context set, and is a consequence worth knowing rather than a bug.
